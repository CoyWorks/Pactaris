# Contributing

The project is proprietary and in discovery/planning. Contributions or modifications require the rights holder's prior written authorization and separately agreed contribution terms. Public repository visibility is not an open-source contribution invitation. Authorized work starts with [the roadmap](docs/ROADMAP.md) and an existing issue.

1. Inspect the current source and relevant issue before proposing implementation.
2. Keep one pull request focused on one buildable milestone. Describe the trigger/problem, resulting behavior, tests and remaining limits.
3. State scope, acceptance criteria, dependencies and implementation notes for new issues. Use a phase and feature area in the title.
4. Use English for code identifiers and repository documentation. Keep user-facing wording adult, professional and consent-based.
5. Add meaningful regression tests for authorization, privacy, transactions, recurrence and safety behavior. Do not substitute source-pattern checks for runtime tests.
6. Use synthetic fixtures. Never commit credentials, database dumps, real household content, private attachments or token-bearing URLs.
7. Document migrations and rollback/cutover implications. Do not deploy or modify the existing Site as an incidental part of a code change.

See LICENSE.txt and issue #50. Respect GitHub's platform terms and all separate third-party licenses; obtain provenance/rights approval before importing code or assets. Do not add an open-source license to project-owned code.
