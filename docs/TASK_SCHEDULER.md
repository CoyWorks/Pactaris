# Task scheduler implementation (#18)

This source change adds versioned standing-authority task series, dated occurrences and autonomous PostgreSQL jobs to the existing Instance worker. It is not activated by the current release manifest: editing deployment files was explicitly excluded from this task. A separately authorized release must register `instance/0016_task_scheduling` with its checksum in `deploy/release.json`, run the preserving migration, and activate Instance before gateway. No prior migration, configuration, Identity, domain, credential or user data is rewritten. Application rollback does not undo generated tasks or schema changes.

The UI detects scheduling support from the Instance's participant list response. Older Instances retain their existing one-off experience; the worker skips scheduling when the migration is absent. The migration runner grants only the new public command wrapper and the bounded scheduler entry point to the non-owner runtime. Internal generation/base commands and FORCE-RLS tables remain inaccessible directly. Backup remains separately read-only. No deployment or production access was performed.

## User workflow and versioning

The participant task editor uses an already adopted directional policy for one-off scheduled, daily or selected-weekday work. Weekly means one occurrence on each selected ISO weekday. A rule contains a start date, optional inclusive end date, IANA timezone, local availability time and elapsed minutes until due (1–10080). The task's stored timezone is independent of UI formatting and subsequent household timezone edits. The server derives parties, agreement version and direct/explicit mode from the exact policy; neither a Dom label nor administration grants authority.

Creation persists the series and an immutable definition revision and immediately generates through the next seven local dates. The series list includes later-starting definitions even when no occurrence falls within that window. Occurrences appear in active lists with availability; My to-do excludes unavailable occurrences, and the server refuses premature starts. Direct occurrences are `assigned`, never individually `accepted`. Explicit policies still create offers. Completion/review uses the existing task lifecycle.

Only the creator can revise a series, with optimistic version and current safety proofs. The same policy and parties remain fixed. Revisions cancel only future untouched assigned/offered occurrences and generate a new version; accepted, started, submitted, completed and past work remains pinned to its original version. Existing noncancelled occurrences on the same local date suppress duplicate generation across revisions. Either party can stop future generation and cancel future untouched work without a fresh consent proof, regardless of pause or capacity. Current/past work retains its existing cancellation control. Departure cancels series and queued jobs against the ended membership; a new membership inherits nothing.

## Calendar, downtime and safety

Each scan uses local calendar dates, rather than adding 24 hours to UTC instants. Nonexistent local DST times are skipped. Ambiguous wall times use PostgreSQL's standard-time interpretation once. Due time is an elapsed duration after availability, including across DST. Daily rules traverse month ends and leap days normally; monthly rules are not offered.

Generation skips any availability instant already elapsed, including earlier today. It never creates a missed-work punishment or a historical backlog. A scan extends a bounded seven-day horizon and revisits each active job hourly; the worker processes at most 16 jobs per configured heartbeat tick. No browser visit, manager call, Redis or extra service is required.

Every batch holds the same household lifecycle lock as consent and membership changes. It checks the configured home Instance, active exact memberships, immutable standing policy version, original household epoch and acceptance fingerprint, current agreement/relationship/limits/expiry and all participant pauses through `activity_guard`. A stale or blocked scope parks the series and job. Clearing a pause or renewing consent alone never resumes it: the creator must explicitly revise under current valid authority. Already generated occurrences still recheck their current task guard on protected transitions.

## Jobs, transactions and capacity

One durable job exists per household/series/version. Occurrences have a unique household/series/version/local-date constraint. Job claim, occurrence, original assignment event, receipt, minimal audit, outbox and cursor advancement are one transaction. Workers acquire a nonblocking household lock before the job row lock; competing workers skip busy households. A crash or lost commit acknowledgement leaves either the complete committed batch or a rollback, so a restarted worker cannot repeat its effects.

Unexpected failures roll back the batch in a subtransaction and persist only a redacted error code and retry metadata. Backoff is 60, 120, 240 and 480 seconds; the fifth failure becomes a dead letter and blocks the series. Capacity failures follow that same bounded retry policy. Explicit revision is the recovery path and retains the failed job/version. The heartbeat reports unsuccessful processing without exposing household content. There is no external delivery claim: notification delivery and reward/points ledgers are still #22/#20/#64. Their processors must consume unique occurrence/completion effect keys and recheck current access before delivery.

Capacity uses the existing locally cached `tasks.active.max`: each active or blocked series counts once, and each nonterminal occurrence counts once, together with private open tasks and standalone participant tasks. Counts are enforced under the common lock for every creation path. This is a conservative combined alpha accounting rule, not a new price or finalized commercial quota. Initial creation/revision is atomic: insufficient space for its initial window rolls it back. Downgrade preserves all content and history, while new generation may retry and then block. Cancelling a series or completing/cancelling occurrences releases their respective capacity. Finished generation releases the series slot while remaining occurrences continue to count.

## Verification and remaining limits

Targeted input/render tests cover exact contracts, invalid dates/timezones/weekdays, bounded duration, explicit schedule semantics and consent-free cancellation. The socket-free PostgreSQL test applies all migrations under a non-superuser schema owner and executes real calendar, privacy, authorization, transaction rollback, deduplication, extension, retries/dead-letter, pause, stale-decision, revocation, departure and downgrade assertions. It separately checks runtime denial of direct tables and internal functions. It does not prove concurrent execution.

`tests/scheduler.integration.ts` uses disposable databases/roles, a temporary migration manifest, concurrent workers, rollback/restart and pause serialization. Cleanup closes the pools and drops the database without `FORCE`, avoiding administrator-termination errors racing graceful socket shutdown; leaked connections still fail cleanup. The existing native HTTPS/two-Instance fixture remains required. Socket creation is prohibited in the development sandbox, so those suites cannot be reported as locally passed. Live supervised-worker reboot/mobile acceptance is also a release gate.

Owner-only unassigned/self-directed tasks remain available without a partner. This slice schedules participant tasks under adopted standing authority; owner-only series drafts, configurable review policies, reward linkage, reminder delivery, monthly recurrence, fleet migration orchestration and personal export/deletion integration remain follow-up work. Thus this change does not close every broader #18/#17 planning criterion.
